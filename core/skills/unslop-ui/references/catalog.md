# ルールの一覧

ルールの ID は固定する。報告と `check-ui.mjs` の出力はこの ID を使う。消したルールの ID は使い回さない。

各ルールの「直す」は次の直し方のどれかで始める。

- 【消す】重複している、または利用者が使わない要素や文を消す。
- 【移す】説明や状態を、それが指す対象の隣へ移す。
- 【枠に入れる】デザインシステムが用意した場所に入れる。説明の枠、既存の部品、間隔や色のトークンを指す。
- 【書き直す】同じ場所のまま、文言か動きを書き直す。文言と操作のルールだけで使う。

例はすべて架空の画面である。

## 根拠の印

- 【指摘】このスキルの作者がエージェントの作った画面を直させた記録。「エージェントがこうしがち」の根拠はこれだけである。確信度（高・中・低）と件数を添える。
- 【癖】モデルのベンダーか、名前の分かるデザイナーの文書が、AI の出力の癖として名指ししている。時期を添える。
- 【規範】デザインシステムやガイドラインが、避けるよう定めているか、出す条件を定めている。AI の癖としての裏付けではない。
- 【通説】記事やスキルが繰り返し挙げるが、データや理由づけが薄い。

出典の URL は [sources.md](sources.md) にある。

文言と操作のルールの多くは、根拠が【規範】と【指摘】だけである。AI の癖として名指しした出典は見つかっていない。そのため、要素や文を出すかどうかを決めるルール（補足文、プレースホルダー、見出しの下の説明文、感嘆符、呼びかけ、通知、確認、読み込みの表示）は「出してよい条件」の形で書く。条件を満たしていれば、エージェントが書いたものでも残す。

見た目のルールの根拠は【癖】である。癖はモデルと時期によって変わるので、時期を見て古くなったルールを外す。

## 0. 要否（どの原則より先に確かめる）

### need-unrequested

頼まれていないボタン、見出し、入口、選択欄、状態のタグ、集計の行がある。

- 直す: 【消す】足した要素ごとに、利用者がそれを使う場面を1つ挙げる。挙げられないものは消す。後で要るとわかったら、その時点で足す。
- 例: 備品の貸し出し画面に「新しい申請」ボタンと「カテゴリを選ぶ」プルダウンが足されている → 両方消す。お知らせの一覧の空の状態に「作成する」ボタンがある → 消す。利用者が作らないものに作成の入口は要らない。
- 例外: 依頼に書かれている要素。既存の同じ種類の画面にある要素。
- 根拠: 【指摘】高（10件、2つのプロジェクト）

### need-double-encoding

色や形で伝わる情報に、数字やタグを重ねている。

- 直す: 【消す】どちらか一方にする。狭い場所では、記号や数字より色で示す。
- 例: 会議室の空き状況の格子の各マスに、色と「空き 3」の両方がある → 数字を消し、色の濃さで示す。凡例を添える。
- 例外: 色だけにすると、色の見分けにくい人に伝わらない（WCAG 1.4.1）。凡例か、アクセシブルな名前かツールチップに、同じ情報を残す。
- 根拠: 【指摘】高（頼まれていない要素の型の一部）／【規範】WCAG 1.4.1

## 1. 近接

離れた要素どうしの関係は、近さとまとまりと名前で示す。言葉では補わない。

### prox-distant-note

離れた場所にある要素との関係を、文で説明している。

- 直す: 【消す】文を消し、関係を置き場所か名前で示す。置き場所や名前で示せないなら、【移す】で文を対象の隣に置く。
- 例: タブの並びから離れたページの下に「この内容は管理者だけに見えます」とある → 文を消し、タブの名前を「管理者用」にする。
- 理由: 説明と対象が離れていると、どの要素の説明かが読み取れない。
- 根拠: 【指摘】高（7件。作者が「説明的な補足が多い」と3回言葉にしている）／【規範】SmartHR（視覚的なグループ。関連の深い要素ほど近づける）

### prox-pre-input-note

入力する前から、使い道や仕組みや操作のしかたを説明する文が出ている。

- 見分け方: その文を消すと、利用者が値やオンとオフを決められなくなるかを問う。決められなくなる文は残す。何が、いつ、どこに届くか、何が起きるか、切ると何が止まるかを書いた、結果についての事実がこれに当たる。消しても決められる文は、使い道、仕組み、操作のしかたの説明なので消す。
- 直す: 【消す】使い道、仕組み、操作のしかたの説明は消す。条件を満たさない入力は、入力した後のエラー文で知らせる。結果についての事実は消さない。対象から離れていれば、【移す】で対象の隣に置く。
- 例: 「表示名」の欄の下に「この名前は一覧に表示されます」「ほかと重ならない名前にしてください」とある → 両方消す。重なったときはエラー文で知らせる。タイムゾーンの欄の「日時の表示に使います」も消す。
- 例: 「週次レポート」のチェックの下に「毎週月曜の朝にメールで届きます」、メール通知のチェックの下に「重要なお知らせはメールで届きます」とある → どちらも結果についての事実なので残す。
- 例外: 利用者が推測できない書式の条件（文字種、桁数、日付の形）は、入力の前に出す。デザインシステムの枠（サポートテキスト、ヒント）に1文で入れる。入力した後のエラー文は消さない。
- 置き場所: 入力に要る情報はラベルと入力欄の間か、入力欄の上に置く。知らなくても入力できる情報は原則として消す。デザインシステムに入力欄の下の補足の枠があり、依頼か既存の画面がその情報を求めるときだけ、その枠に入れる。
- 根拠: 【指摘】高（同上。入力前の説明は消し、入力後のエラー文は残す、という線は作者自身が引いた）／【規範】GOV.UK（ヒントは多数の利用者に要るときだけ）、DADS（推測できない条件は先に示す。サポートテキストはラベルと入力欄の間）、SmartHR（FormControl。入力に要る説明は上、知らなくても操作できる補足は下）

### prox-status-control

状態の表示と、その状態を変えるボタンが離れている。

- 直す: 【移す】状態の表示を、それを変えるボタンの隣に置く。
- 例: 「同期中」の表示が画面の上部にあり、停止ボタンが右下にある → 両方を見出しと同じ行の右端にまとめる。
- 根拠: 【指摘】中（配置の型、8件。下位の型が混ざる）

## 2. 整列

### align-edges

アイコンが文字から浮いている。並んだ要素の上端、中心、ベースラインがずれている。

- 確かめ方: スクリーンショットを拡大し、隣り合う要素の線を比べる。アイコンは本文の1行目の中心か、隣のアイコンの中心に揃っていれば合格。
- 直す: 【枠に入れる】既存の部品の揃え方（`items-center` など）と、間隔のトークンを使う。数値を足して合わせない。
- 例: 一覧の行末のアイコンが本文より 2px 上に浮く → 行を `items-center` にし、アイコンの大きさを本文の行の高さに合わせる。
- 根拠: 【指摘】高（14件、最も多い。AI っぽさというより、仕上げの確認の不足）

### align-indent

開いた中身と見出しで、インデントや余白が揃っていない。

- 直す: 【枠に入れる】見出しと中身で、同じ間隔のトークンを使う。
- 例: 折りたたみの見出しには矢印の分の字下げがあるのに、開いた中身には字下げがない → 中身を見出しの文字の位置から始める。
- 根拠: 【指摘】高（align-edges と同じ型の一部）

### align-narrow-width

狭い幅で、要素が重なる、はみ出す、不要な縦横のスクロールが出る、短い選択肢が1行に収まらない。

- 確かめ方: 390px 前後の幅でもスクリーンショットを撮る。
- 直す: 【枠に入れる】既存の部品の折り返しと、幅ごとの並べ方を使う。
- 根拠: 【指摘】高（align-edges と同じ型の一部）

## 3. 反復

同じ役割のものは同じ部品、同じ言葉、同じ場所にする。

### rep-existing-component

既存の画面に同じ役割の部品、置き場所、動きがあるのに、新しく作っている。

- 確かめ方: 作る前に、既存の画面で同じ役割のものを探す。空の状態、一覧の見出し、追加の入口、詳細の出し方、選択の部品を比べる。
- 直す: 【枠に入れる】既存の部品と置き場所を使う。同じ操作は、どの入口から押しても同じ画面を開く。
- 例: 新しい一覧の空の状態だけ、枠線のボタンが左に寄っている。ほかの一覧では、中央に塗りのボタンがある → ほかの一覧に合わせる。
- 例外: デザインシステムが別の部品を指定しているとき。
- 根拠: 【指摘】高（11件、2つのプロジェクト）

### rep-layout-by-state

状態によって、レイアウト、ボタンの種類、ボタンの位置が変わる。

- 直す: 【枠に入れる】レイアウトは変えず、違いは disabled や読み取り専用の状態で示す。
- 例: 承認済みの申請を開くと、保存ボタンが右上に移り、枠線のボタンに変わる → 位置と種類は変えず、disabled にする。
- 根拠: 【指摘】高（rep-existing-component と同じ型の一部）

### rep-wording-drift

同じ動作を、場所ごとに違う言葉で書いている。元の操作を打ち消す言い方（「解除」）で、結果がわからない。

- 直す: 【枠に入れる】既存の画面の言葉に揃える。ダイアログのタイトルと実行ボタンの動詞を揃える。「解除」のような打ち消しの言葉は、結果がわかる動詞（「アーカイブ」「停止」）にする。
- 例: ボタンは「貸し出しを解除」、ダイアログは「返却の登録」、完了の通知は「戻しました」→ すべて「返却」にする。
- 例外: 直した言葉が差分の外の画面と食い違うときは、差分の外は直さず、報告の「残したもの」に書く。
- 根拠: 【指摘】高（同上）／【規範】SmartHR（ダイアログのタイトルとボタンを揃える）、Anthropic frontend-design（流れの中で同じ語を使う）

## 4. コントラスト

大事なものが目立つように、差は大きさ、太さ、余白、置き場所で付ける。飾りで付けない。

### contrast-boxes

要素をカードや枠で囲んでいる。階層に関係なく、すべてが同じ角丸と影のカードに入っている。

- 直す: 【消す】囲みを外し、余白と並びで区切る。囲みは、無いとまとまりがわからないときと、独立して動かせるまとまりにだけ使う。
- 例: 予約の詳細の各項目を1つずつカードで囲み、その下の注意書きも枠で囲んでいる → 囲みを外し、項目を定義リストで並べる。
- 例外: デザインシステムのカード部品を、その用途どおりに使っているとき。
- 根拠: 【指摘】中（6件、1つのプロジェクトに偏る）／【癖】Anthropic frontend-design の「同じ角丸のカードに切り分ける」型
- 時期: 2026 年（2026-09 の frontend-design が挙げる）

### contrast-loud-minor-action

めったに使わない操作が、主な操作と同じ大きさと強さで並んでいる。

- 直す: 【枠に入れる】頻度の低い操作は既存の目立たないボタン（テキストボタン、メニューの中）にする。押せる範囲は文字より少し広く取る。
- 例: 経費の各行に、枠線付きの標準の「編集」「削除」ボタンが並ぶ → 灰色の小さなテキストボタンにするか、行のメニューに入れる。
- 根拠: 【指摘】中（contrast-boxes と同じ型の一部）

### contrast-color-meaning

色を意味と結び付けずに選んでいる。原色、濃くなるほど濁る段階の色、2つの状態を混ぜた色。

- 直す: 【枠に入れる】デザインシステムの色のトークンを使う。段階は色相を保ち、明るさだけを変える。2つの状態をあわせ持つものは、2色で塗り分ける。
- 根拠: 【指摘】中（5件）

### contrast-landing-layout

業務の画面を宣伝のページのように組んでいる。中央寄せの大きな見出し、アイコン付きの同じ形のカード3枚、見出しの上のピル型のバッジ、大きな数字と小さなラベルの統計の帯。

- 直す: 【消す】最初に作業の対象（表、フォーム、一覧）を置く。統計の数字は、その画面で判断に使うときだけ置く。
- 根拠: 【癖】Krebs の計測、Anthropic frontend-design
- 時期: 2025〜2026 年

### contrast-decoration

意味のない飾りの決まり文句がある。カードの1辺だけの色線、見出しの1語だけの色、全見出しの上の英字の小見出し（eyebrow）、順序でない内容の 01/02/03、色付きの光る影、すりガラス。

- 直す: 【消す】飾りを消す。強調は大きさと太さで付ける。番号は手順と時系列にだけ使う。
- 例外: デザインシステムかブランドが定めているとき。和文の画面では、英字の大文字化や字間の調整は効かないので、使う理由がない。
- 根拠: 【癖】Anthropic frontend-design、Krebs の計測、Impeccable
- 時期: 2025〜2026 年

### contrast-default-palette

デザインシステムに無い配色と書体を、モデルの既定のまま使っている。

- 時期ごとの既定は次のとおり。
  - 2025 年: Inter、白地、紫のグラデーション（2025-11 の Anthropic の記事）。
  - 2026 年: クリーム地と高コントラストのセリフとテラコッタ、黒地と単色の酸性の緑、罫線と角丸ゼロの新聞風、同じ角丸と薄い影の SaaS のカード一式（2026-09 の frontend-design）。
- 直す: 【枠に入れる】デザインシステムの色と書体のトークンを使う。デザインシステムが無ければ、無彩色とアクセント1色にする。見た目の方向を新しく決めるときは frontend-design スキルに任せる。
- 例外: ブランドの色が紫であるとき。業務の画面では、既定の書体（Inter、システムフォント）が合っていることも多い。
- 根拠: 【癖】Anthropic のブログと cookbook、Anthropic frontend-design

### contrast-purple-gradient

紫、すみれ色、藍色のグラデーションを使っている。

- 直す: 【枠に入れる】contrast-default-palette と同じ。
- 例外: ブランドの色が紫であるとき。
- 根拠: 【癖】Anthropic のブログと cookbook、The Fountain Institute、Krebs の計測（GIGAZINE の集計でグラデーション 28%）
- 時期: 2024〜2025 年。2026 年のモデルは紫を避け、contrast-default-palette の 2026 年の既定に寄る。
- 検出: check-ui.mjs

### contrast-gradient-text

文字にグラデーションをかけている（`bg-clip-text`、`background-clip: text`）。

- 直す: 【消す】文字は単色にする。強調は大きさと太さで付ける。
- 根拠: 【癖】Krebs の計測、Impeccable
- 時期: 2025〜2026 年
- 検出: check-ui.mjs

### contrast-sparkle

AI の機能を、きらめきのアイコン（✨、Sparkles）で示している。

- 直す: 【消す】機能の名前を文字で書く。デザインシステムに AI の機能を示すアイコンがあれば【枠に入れる】。
- 理由: 利用者はこのアイコンを「AI」と結び付けて読まない。
- 根拠: 【癖】NN/g（2024 年の調査）
- 時期: 2024 年〜（NN/g の調査の時点）
- 検出: check-ui.mjs

## 5. 文言

UI の文字列（コンポーネントの中の文字、i18n のファイル）はこのスキルで扱う。ヘルプページなどの段落の文章は yomiyasu スキルに任せる。

### copy-helper-every-field

フォームのすべての欄に補足文が付いている。

- 出してよい条件: その欄で多数の利用者が迷うときだけ、1文で出す。欄の名前の言い直しは出さない。判断は prox-pre-input-note に従う。
- 直す: 【消す】条件を満たさない補足を消す。書式の条件は【枠に入れる】。
- 例: 経費のフォームの「件名」「金額」「メモ」のすべての下に補足がある → 金額の「税込みで入力」だけを残し、ほかは消す。
- 根拠: 【指摘】高（prox-pre-input-note と同じ型）／【規範】GOV.UK、Impeccable（補足は欄の言い直しでなく、暗黙の問いに答える）
- 検出: check-ui.mjs（欄が3つ以上あり、補足が欄の数以上あるファイル）

### copy-placeholder-instruction

プレースホルダーに、操作の説明か入力の条件が書いてある。

- 出してよい条件: プレースホルダーには入力の例か、何を書く欄かだけを書く。
- 直す: 【消す】操作の説明（「Enter で送信」）は消す。【枠に入れる】入力の条件（「半角数字」「必須」）はラベルかサポートテキストへ移す。
- 例: 備品の検索欄のプレースホルダーが「品名を入力してください（Enter で検索）」→「品名」にする。
- 理由: 入力を始めると消えるので、読みたいときに読めない。
- 根拠: 【指摘】高（prox-pre-input-note と同じ型）／【規範】GOV.UK、DADS、SmartHR、NN/g
- 検出: check-ui.mjs

### copy-restates-heading

見出しやラベルのすぐ下に、それを言い直すだけの説明文がある。

- 出してよい条件: 見出しに無い情報（期限、対象、結果）があるときだけ置く。
- 直す: 【消す】言い直しを消す。新しい情報があれば、その情報だけを残す。
- 例: 「会議室の予約」の下に「会議室の予約を管理できます。」→ 消す。「請求書」の下の「毎月25日に締め、翌月10日に発行します。」は残す。
- 例外: デザインシステムが画面説明の枠と定型文を求めているときは、枠を残し、定型文に合わせる。
- 根拠: 【指摘】高（先回りの補足の型の一部）／【規範】Atlassian、Apple、SmartHR（ダイアログにサブタイトルを使わない）、Impeccable
- 検出: check-ui.mjs（見出しの語を含み、ほかの情報がほぼ無い説明文）

### copy-prose-wall

画面を段落の文で埋めている。同じ内容をカードの後でもう一度文で言い直している。

- 直す: 【消す】言い直しを消す。要点を先に置き、並べられるものは表やリストにし、詳細は畳む。
- 例: 備品の貸し出し状況の画面の先頭に、状況を説明する4文の段落があり、その下の表と同じことを言っている → 段落を消し、表の上に1行の要約だけを置く。
- 根拠: 【指摘】高（8件。業務の画面に限ると中）

### copy-exclamation

業務の画面の文言に「！」がある。

- 出してよい条件: デザインシステムかブランドの文体が認めているときだけ。失敗と警告には付けない。
- 直す: 【書き直す】「！」を取り、平叙の「〜しました」にする。
- 根拠: 【規範】Microsoft、Mailchimp、Atlassian。AI の癖として挙げた出典は1件だけで（Tremoloo）、【通説】にも届かない
- 検出: check-ui.mjs

### copy-cheer

呼びかけ、励まし、挨拶の文言がある（「〜しましょう」「さあ、」「ようこそ」）。

- 出してよい条件: 学習や趣味など、文体として励ましを選んだ製品だけ。業務の画面には置かない。
- 直す: 【書き直す】見出しは画面の名前にする。空の状態には、空である理由と次の操作1つを書く。
- 例: 予約の一覧が空のとき「さあ、最初の予約を作成しましょう！」→「予約はありません」と「予約する」ボタン。
- 根拠: 【通説】挨拶の見出しを AI の癖として挙げる記事とスキル（Tremoloo、heydamir/unslop）
- 検出: check-ui.mjs

### copy-hype

業務の画面で、機能を売り込む言葉を使っている（「かんたんに」「スムーズに」「シームレス」「たった1クリックで」）。

- 直す: 【書き直す】何をするかを平易に書く。売り込みの言葉を、別の売り込みの言葉に言い換えない。
- 根拠: 【癖】Anthropic frontend-design（売り込まずに何であるかを書く）／【規範】Google の開発者スタイルガイド（simply、easy を避ける）

### copy-kochira-link

リンクの文字が「こちら」になっている。

- 直す: 【書き直す】リンクの文字を、リンク先の名前にする（「精算のルール」）。
- 理由: リンクだけを読み上げる支援技術では、行き先がわからない（WCAG 2.4.4）。
- 根拠: 【規範】SmartHR、WCAG 2.4.4
- 検出: check-ui.mjs

### copy-error-apology

エラーの文言が謝っているか、おどけている（「申し訳ありません」「おっと」）。

- 直す: 【書き直す】謝罪と間投詞を消し、何が起きたかと、どう直すかを書く。
- 根拠: 【癖】Anthropic frontend-design（エラーは謝らない）／【規範】GOV.UK、Apple、Material 3
- 検出: check-ui.mjs

### copy-error-vague

エラーの文言に、何が起きたかが書かれていない（「エラーが発生しました」）。

- 直す: 【書き直す】何が起きたか、なぜか、どう直すかを書く。全部を書けないときは、原因、対処、事象の順に優先して残す。
- 例: 「エラーが発生しました。もう一度お試しください。」→「CSV の3行目の日付を読めませんでした。YYYY-MM-DD の形にしてください。」
- 根拠: 【規範】SmartHR、DADS、GOV.UK
- 検出: check-ui.mjs（文言が漠然とした語で始まるもの）

### copy-are-you-sure

確認の文言に、対象と結果が書かれていない（「本当によろしいですか？」）。

- 直す: 【書き直す】対象と、実行すると何が起きるかを書く。ボタンは動詞にする。
- 例: 「本当によろしいですか？」と「はい」「いいえ」→「3件の予約を取り消しますか？ この操作は元に戻せません。」と「取り消す」「キャンセル」。
- 根拠: 【規範】SmartHR、NN/g、Material 3
- 検出: check-ui.mjs

### copy-verbose-honorific

回りくどい敬語がある（「させていただきます」「することができます」）。

- 直す: 【書き直す】「します」「できます」にする。
- 根拠: 【規範】SmartHR
- 検出: check-ui.mjs

### copy-empty-filler

空の状態に「ここに〜が表示されます」とだけ書いてある。

- 直す: 【書き直す】空である理由と、次の操作を1つ示す。利用者が作らないものの一覧なら、「〜はありません」だけにする。
- 根拠: 【規範】Atlassian、Apple、NN/g（空の状態は理由と次の行動を示す）
- 検出: check-ui.mjs

### copy-emoji

画面の文字列、見出し、ナビゲーションに絵文字がある。

- 直す: 【消す】絵文字を消す。アイコンが要るなら、デザインシステムのアイコンセットから選ぶ（【枠に入れる】）。
- 例外: 利用者が入力した文字列。絵文字の入力を受け付ける機能。
- 根拠: 【癖】The Fountain Institute、Krebs の計測（頻度は低い）
- 時期: 2025〜2026 年
- 検出: check-ui.mjs

### copy-internal-term

内部の名前や記号を、画面に出している（テーブル名、設定のキー、「A1」のような管理番号）。

- 直す: 【書き直す】利用者が使う言葉で名付ける。
- 根拠: 【指摘】低（1件）／【癖】Anthropic frontend-design（内部構造の名前を見せない）／【規範】SmartHR

## 6. 操作

### interact-toast-every-action

操作のたびに、成功の通知（トースト、スナックバー）を出している。

- 出してよい条件: 画面の変化で結果がわからないとき（クリップボードへのコピー、裏で進む処理）。出すなら、操作した場所の近くに出す。
- 直す: 【消す】別の画面へ移るなど、画面の変化で結果がわかるなら出さない。同じ画面に残るなら、ボタンの文字を「保存済み」に変えるか、ボタンの横に小さく出す（【移す】）。エラーは入力欄か操作した部品の近くに出す。
- 例: 保存すると右上にスナックバーが出て、そこにある編集ボタンを隠す → 保存して一覧へ戻るので、何も出さない。
- 根拠: 【指摘】中〜高（演出と通知の型、5件）／【規範】SmartHR、Material 3、NN/g
- 検出: check-ui.mjs（成功の通知の呼び出しが同じファイルに2つ以上）

### interact-confirm-undoable

取り消せる操作の途中に、確認のダイアログを挟んでいる。

- 出してよい条件: 取り消せない操作（削除、多人数への一括操作や配付、公開）だけ。件数と、何が起きるかを書く。
- 直す: 【消す】差分が足した確認だけを消し、実行後に「元に戻す」を出す。差分の前からある確認は、挙動の変更になるので消さない。勧める案として報告の「確かめたいこと」に書く。
- 根拠: 【指摘】中（演出と通知の型の一部）／【規範】NN/g、Apple、DADS、SmartHR

### interact-motion

視線を誘う点滅、すべての区画のフェードイン、すべてのカードのホバーの動き、ゆっくり消える演出がある。

- 直す: 【消す】動きは利用者の操作への応答に限り、短くする。
- 根拠: 【指摘】中（演出と通知の型の一部）／【癖】Anthropic frontend-design（区画ごとのフェードインとカードのホバーは生成の既定）
- 時期: 2026 年

### interact-focus

利用者の操作で入力欄が開いたのに、フォーカスが当たらない。

- 直す: 【書き直す】開いた入力欄にフォーカスを当てる。スマートフォンでは、キーボードが出た状態にする。
- 根拠: 【指摘】中（2件、2つのプロジェクト。作者が UI の方針の例に挙げている）

### interact-few-options

ひと目で見渡せる数（4つ程度まで）の選択肢を、プルダウンに隠している。

- 直す: 【枠に入れる】既存のチップかラジオボタンで並べる。狭い幅でも1行に収める。
- 例外: デザインシステムが選択の部品を指定しているとき。置き場所が狭く、並べると折り返すとき。
- 根拠: 【指摘】中（2件、2つのプロジェクト）

### interact-missing-states

正常な場合しか作っていない。空、読み込み中、エラーの状態が無い。待っている間、待っていることが見えない。

- 出してよい条件: 読み込みの表示は1秒以上かかる処理にだけ出す。2〜10秒ならスピナー、10秒を超えるなら進み具合を出す。
- 直す: 【枠に入れる】既存の空の状態、読み込み中、エラーの部品で3つの状態を作る。
- 理由: 引き算のルールの逆向きである。必要な状態の表示まで消さない。
- 根拠: 【指摘】中（AI の返答を待つ間に何も見えない、という逆向きの指摘）／【通説】Kosta Canatselis／【規範】NN/g（1秒未満は出さない）

## 7. 食い違い

出典どうしや、作者の指摘と出典が食い違う点。どれも、デザインシステムと既存の画面、依頼、このスキルの既定の順で決める。

| 論点 | 一方 | 他方 | このスキルの扱い |
|---|---|---|---|
| 入力前の説明 | 作者: 入力前の説明は書かない | DADS: 推測できない条件は先に示す | 使い道と仕組みの説明は消す。推測できない書式の条件だけ、枠に1文で先に出す |
| 色だけで示す | 作者: 狭い場所では数字より色 | WCAG 1.4.1: 色だけで伝えない | 色にしてよい。凡例、アクセシブルな名前、ツールチップのどれかに同じ情報を残す |
| 画面の説明文 | SmartHR: 画面説明の枠と定型文を置く | 見出しの言い直しを消す | デザインシステムの枠を残し、定型文に合わせる |
| プレースホルダーの入力例 | Apple: 入力の形の例は置いてよい | SmartHR、DADS、GOV.UK: 例もプレースホルダーに置かない | デザインシステムに従う。無ければ作者の線（入力の例と欄の内容は置いてよい） |
| ボタンの「する」 | SmartHR: サ変の「する」を省く（「追加」） | Ameba Spindle: 漢語には「する」を付ける | デザインシステムに従う。無ければ既存の画面の多い方に揃える。このスキルは既定を持たない |
| エラーの位置 | SmartHR: 入力欄の上 | DADS: 入力欄の下 | デザインシステムに従う。無ければ既存のフォームに揃える。どちらでも入力欄の隣に置く |
| 検証のタイミング | SmartHR: フォーカスが外れたとき | DADS: 送信したとき | デザインシステムに従う。無ければ既存のフォームに揃える。既存も無ければ、報告の「確かめたいこと」に書く |
| 成功の通知 | 一般のガイド: 成功を知らせる | SmartHR、Material 3、作者: 画面の変化でわかるなら出さない | 画面の変化でわからないときだけ出す |
| 確認のダイアログ | 一般のガイド: 破壊的な操作は確認する | 作者、NN/g、Apple: 取り消せる操作には出さない | 新しく足す確認は、取り消せない操作だけにする。既存の確認は消さず、「確かめたいこと」に書く |

## 8. 引きすぎ

引くのは情報で、作りの厚みではない。次の型は、このスキルの規則そのものが生む。

- 書式の条件まで消し、エラーで初めて条件を知らせる。→ 推測できない条件は先に出す（prox-pre-input-note）。
- 結果についての事実（届く曜日、届く先、切ると止まるもの）を、入力前の説明として消す。→ 消さない。対象から離れていれば隣へ移す（prox-pre-input-note）。
- 規範に合わせるために、確認のダイアログ、保存の単位、検証のタイミング、画面の移り方を黙って変える。→ 変えずに「確かめたいこと」に書く。
- ラベル、必須の表示、エラー文、アイコンだけのボタンのアクセシブルな名前を消す。→ 消さない。
- 囲みと一緒に、余白と見出しの階層まで削る。灰色の平板なテンプレートに戻る。→ 余白と大きさの差は残す。
- 「！」や呼びかけを消した結果、体言止めや命令形が続く。→ 「〜しました」「〜できます」の平叙にする。
- 売り込みの言葉を、別の売り込みの言葉に言い換える。→ 何をするかを書く。
- 空の状態の次の操作や、待っている間の表示まで消す。→ interact-missing-states。
- 色だけで示し、色の見分けにくい人に伝わらなくなる。→ need-double-encoding の例外。
- 紫を避けた結果、2026 年の別の既定（クリーム地とテラコッタ）に寄る。→ デザインシステムのトークンを使う。
- AI っぽさの無い画面を、違いを出すために変える。差分の外まで直して、差分が膨らむ。→ 変えない。差分の外は報告に書く。
- ルールに当たらない不具合を直すために節を組み替え、ボタンを対象から離すなど、近接や整列を悪くする。→ 組み替えずに「確かめたいこと」に書く。変える前と後のスクリーンショットを比べて確かめる。
